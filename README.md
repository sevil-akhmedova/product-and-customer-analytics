## 1. A/B-тестирование новой механики оплаты

**Задача:** определить, повлияла ли новая механика оплаты на поведение пользователей и стоит ли запускать её на всех участников платформы.

В эксперименте сравнивались две группы: контрольная A со старой механикой оплаты и тестовая B с новой.

### Подготовка данных

Для анализа объединили данные о принадлежности пользователей к группам, их активности и оплатах. Проверили структуру таблиц и наличие дубликатов.

При проверке обнаружилось, что **149 пользователей совершили оплату, но отсутствовали в списке активных**: 29 человек в группе A и 120 в группе B.

Основной анализ проводился по активным пользователям. Это ограничение учитывалось при интерпретации результатов.

### Метрики и статистические проверки

Для оценки результатов рассчитаны три показателя:

- **CR:** конверсия активных пользователей в оплату.
- **ARPU:** средняя выручка на активного пользователя.
- **ARPPU:** средняя выручка на платящего пользователя.

Для проверки различий по CR использовался критерий χ², а для ARPU и ARPPU применялся bootstrap с 95% доверительными интервалами.

### Результаты

| Метрика | Группа A | Группа B | Статистическая значимость |
|---|---:|---:|---|
| CR | 5,07% | 4,62% | Нет |
| ARPU | 47,35 | 58,06 | Нет |
| ARPPU | 933,59 | 1 257,88 | Есть |

**Что удалось выяснить**

Новая механика оплаты не привела к статистически значимому изменению конверсии. ARPU в тестовой группе оказался выше, но статистическая значимость этого различия не подтвердилась.

При этом **ARPPU вырос примерно на 35%, и это различие оказалось статистически значимым**.

### Вывод

Платящие пользователи тестовой группы в среднем приносили больше выручки. Однако значимого роста ARPU не обнаружено, поэтому пока недостаточно оснований утверждать, что новая механика увеличивает выручку на активного пользователя.

**Полный запуск новой механики оплаты по результатам эксперимента не рекомендован.** Для принятия решения стоит дополнительно исследовать причины роста ARPPU и проверить эффект на большем объёме данных.

Подробные расчёты, статистические проверки и графики представлены в [ноутбуке A/B-теста](notebooks/ab-test-payment-mechanism.ipynb).

## 2. Автоматизация расчёта продуктовых метрик

**Задача:** упростить обновление показателей после поступления дополнительных данных об участниках эксперимента.

Для этого разработаны три функции на Python:

- `preprocess_data()`: приводит предусмотренные форматы названий столбцов к единому виду.
- `calculate_metrics()`: загружает дополнительный CSV-файл, объединяет данные и пересчитывает CR, ARPU и ARPPU.
- `plot_metrics()`: строит сравнительные графики продуктовых метрик для контрольной и тестовой групп.

### Результат

При поступлении нового файла можно повторно выполнить расчёт и получить обновлённые показатели без ручного объединения таблиц.

Функция предобработки поддерживает варианты названий идентификаторов `id` и `student_id`. Если структура входных данных отличается от предусмотренной, её потребуется адаптировать.

Код и примеры использования представлены в [ноутбуке с функциями](notebooks/python-data-update.ipynb).

## 3. SQL-сегментация клиентов

**Задача:** распределить клиентов интернет-магазина по сегментам, которые можно использовать для персонализированных коммуникаций.

Это отдельное исследование, не связанное с A/B-тестом механики оплаты.

Сегментация выполняется по состоянию на **31 марта 2024 года** с учётом количества доставленных заказов и даты регистрации пользователя.

### Логика сегментации

| Сегмент | Условие |
|---|---|
| Постоянный | 3 и более доставленных заказа |
| Разовый | 1–2 доставленных заказа |
| Неактивный | Нет доставленных заказов, регистрация более 30 дней назад |
| Новый | Нет доставленных заказов, регистрация не более 30 дней назад |

Для формирования сегментов используются таблицы `customers`, `orders` и `customer_actions`.

Запрос написан на PostgreSQL с использованием CTE, `LEFT JOIN`, `CASE`, агрегатных функций и операций с датами.

Агрегация заказов и пользовательских событий выполняется отдельно. Это позволяет избежать дублирования строк при объединении таблиц.

### Результат

Подготовлен [SQL-запрос](sql/customer_segmentation.sql), который формирует клиентские сегменты и рассчитывает дополнительные показатели активности.

Такую сегментацию можно использовать как основу для CRM-коммуникаций, например для отдельных предложений новым, разовым и постоянным покупателям.
