## 1. A/B-тестирование новой механики оплаты

**Задача.** Сравнить контрольную группу A (прежняя механика) и экспериментальную группу B (новая механика) и определить, достаточно ли оснований для запуска изменения на всех пользователей.

**Что сделано:**

- Объединены данные о группах, активности и оплатах; выполнены проверки структуры данных и дубликатов.
- Обнаружены 149 пользователей с оплатами, отсутствующих в списке активных (29 в A и 120 в B). Основной анализ проведён по активным участникам эксперимента; ограничение отмечено при интерпретации.
- Рассчитаны CR (конверсия в оплату), ARPU (выручка на активного пользователя) и ARPPU (выручка на платящего пользователя).
- Для CR применён критерий хи-квадрат; для сравнения средних денежных метрик — bootstrap с 95%-ми доверительными интервалами.

**Полученные метрики:**

| Метрика | Группа A | Группа B |
|---|---:|---:|
| CR | 5,07% | 4,62% |
| ARPU | 47,35 | 58,06 |
| ARPPU | 933,59 | 1 257,88 |

**Результат.** Статистически значимого различия CR и ARPU не обнаружено; увеличение ARPPU статистически значимо. Поскольку значимый рост выручки на активного пользователя не подтверждён, **полный запуск новой механики оплаты на основании этого эксперимента не рекомендован**.

Подробные расчёты, статистические проверки и графики доступны в [ноутбуке A/B-теста](notebooks/ab-test-payment-mechanism.ipynb).

## 2. Повторный расчёт продуктовых метрик

В отдельном [ноутбуке](notebooks/python-data-update.ipynb) реализованы три функции:

- `preprocess_data()` — приводит предусмотренные в задании форматы столбцов к единому виду;
- `calculate_metrics()` — при вызове загружает дополнительный CSV, объединяет данные и пересчитывает CR, ARPU, ARPPU;
- `plot_metrics()` — строит столбчатые графики для сравнения групп.

При поступлении обновлённого дополнительного файла достаточно повторно вызвать расчёт с путём к этому файлу. Функция предобработки поддерживает предусмотренные варианты названий столбцов (`id` и `student_id`), а для нестандартных заголовков потребуется адаптация.

## 3. SQL: сегментация клиентов для CRM

**Отдельная бизнес-задача**, не использующая данные A/B-теста: распределить клиентов магазина на четыре группы для персонализированных коммуникаций по состоянию на **31 марта 2024 года**.

| Сегмент | Условие |
|---|---|
| Постоянный | Не менее 3 доставленных заказов |
| Разовый | 1–2 доставленных заказа |
| Неактивный | Нет доставленных заказов, регистрация более 30 дней назад |
| Новый | Нет доставленных заказов, регистрация не более 30 дней назад |

Запрос объединяет таблицы `customers`, `orders`, `customer_actions`. Для расчёта используются CTE, `LEFT JOIN`, `CASE`, `COUNT`, `AVG`, `COALESCE` и операции с датами. Отдельная агрегация заказов и событий помогает избежать размножения строк при соединении.

[Открыть SQL-запрос](sql/customer_segmentation.sql).

**Ограничение проверки:** при подготовке версии для портфолио в запрос добавлены ограничения по дате среза. После окончания доступа к учебной базе эта редакция SQL **не запускалась повторно на исходных данных**. Поэтому здесь не приводятся непроверенные количества клиентов по сегментам.
